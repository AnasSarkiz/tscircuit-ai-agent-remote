Create a new **tscircuit PCB project** for a small handheld AI hardware controller.

## Project name

**tscircuit-ai-agent-remote**

The device is a compact physical interface for an AI agent.

The main interaction should be:

**Press TALK → speak → send request to AI backend over Wi-Fi → show response/action on display → user physically approves or rejects the action.**

This is NOT intended to run a large AI model locally. The board is an input/output client that communicates with a cloud/backend AI service over Wi-Fi.

The design should be generic enough to work with different AI backends.

---

# Main features

The device must include:

- ESP32-S3 MCU/module
- Wi-Fi
- Bluetooth LE
- USB-C
- Rechargeable LiPo battery
- Battery charging
- Battery protection
- 3.3 V regulated supply
- Small color display
- Two digital MEMS microphones
- Small speaker
- Audio amplifier
- Haptic vibration motor
- RGB status LED
- Rotary encoder with push button
- Large TALK button
- APPROVE button
- REJECT button
- Physical microphone-disable/privacy switch
- Power button or power switch
- Battery level measurement
- Programming/debug interface
- Useful debug/test points

Keep the device reasonably simple. Do not add unnecessary sensors, cameras, GPS, cellular, SD card, HDMI, or other features unless they are required.

# Intended UI

The display should be approximately **1.54–1.9 inches**.

Example interaction:

```text
┌────────────────────────┐
│ ● LISTENING            │
│                        │
│ Buy the MacBook for    │
│ €2,199?                │
│                        │
│   ✓ APPROVE   ✕ REJECT │
└────────────────────────┘

        ◉ TALK
```

The rotary encoder should allow scrolling through:

- AI responses
- Pending actions
- Notifications
- Simple menus

Pressing the encoder selects an item.

# Status indication

Use RGB LED states approximately like:

- Blue = ready
- Cyan = listening
- Purple = processing
- Green = completed/approved
- Red = error/rejected
- Orange = disconnected

The exact firmware behavior does not need to be implemented yet, but the hardware must support it cleanly.

# MCU

Prefer an **ESP32-S3 module with integrated flash and antenna** rather than designing the RF section from the bare chip.

Prefer something widely available from JLCPCB/LCSC.

Examples can include an ESP32-S3-WROOM family device, but choose the exact module based on:

- JLCPCB availability
- sufficient GPIO
- I2S support
- SPI support
- USB support
- Wi-Fi
- BLE
- PSRAM if useful for display/audio buffering

Make sure antenna placement follows the manufacturer's keepout recommendations.

Do not place copper, components, battery, display metal, or ground beneath the antenna keepout region.

---

# Audio input

Use **two digital MEMS microphones**.

Prefer I2S/PDM microphones supported by ESP32-S3.

Place the microphones toward the upper/front edge of the PCB with acoustic openings that can align with enclosure holes.

Provide appropriate decoupling.

The physical **MIC PRIVACY switch must electrically disable the microphones**.

Do not make privacy disable purely firmware-controlled.

Preferred implementation:

- disconnect microphone power rail, or
- use a load switch controlling microphone power

The MCU should optionally be able to detect the privacy-switch state.

---

# Audio output

Include:

- small 8-ohm speaker connection
- efficient mono audio amplifier
- ESP32 digital audio output where practical

Prefer an I2S Class-D amplifier such as a MAX98357-type solution or another suitable JLCPCB-supported component.

Provide a speaker connector/pads that can connect to a small enclosure-mounted speaker.

Do not place the speaker directly on the PCB unless there is a strong mechanical reason.

---

# Display

Use a readily available small SPI TFT display.

Target:

- 1.54" to 1.9"
- approximately 240×240 or similar
- SPI
- backlight control from MCU

Prefer an ST7789-compatible display/module if practical.

The display should use a connector if this makes enclosure assembly easier.

If using FPC:

- use the correct FPC connector
- verify pin order
- verify contact orientation
- document the exact compatible display

# Controls

Include:

### TALK

Large tactile push button.

This should be the most visually and mechanically prominent control.

### APPROVE

Dedicated green/user-facing approval button.

### REJECT

Dedicated reject/cancel button.

### Rotary encoder

Use:

- A
- B
- push switch

Add hardware debouncing/filtering if appropriate.

### Power

Provide a user-accessible power switch or suitable soft-power architecture.

Keep the implementation simple and reliable.

---

# Haptic feedback

Include a small vibration motor output.

Prefer a coin vibration motor connected through:

- suitable transistor/MOSFET driver
- flyback protection if required

Expose a connector or solder pads for the motor.

Do not drive the motor directly from an ESP32 GPIO.

---

# USB-C

Use ONE USB-C connector.

Functions:

- battery charging
- power input
- ESP32 USB programming/debugging if practical

USB-C should operate as a USB device/sink only.

Use correct:

- CC1/CC2 resistors
- ESD protection
- USB data routing
- power protection

Do not add USB-PD unless there is a real need.

Normal 5 V USB-C input is sufficient.

---

# Battery system

Use a single-cell LiPo battery.

Target battery size:

approximately **500–1000 mAh**

Include:

- LiPo connector
- charger
- battery protection where needed
- load sharing / power path if practical
- regulated 3.3 V rail

The device should be able to operate while connected to USB-C.

Choose a charger/power-management IC that is:

- common
- well documented
- JLCPCB/LCSC available
- appropriate for USB-C 5 V input
- safe for a small consumer handheld device

Add battery voltage measurement to an ESP32 ADC through an appropriate divider.

Consider a load-switch or power-latch solution only if it does not unnecessarily complicate the design.

---

# Power architecture

Expected structure:

```text
USB-C 5V
   │
   ├── ESD / input protection
   │
   ▼
LiPo charger / power path
   │
   ├── Battery
   │
   ▼
3.3V regulator
   │
   ├── ESP32-S3
   ├── display
   ├── microphones
   ├── encoder/buttons
   ├── LEDs
   └── supporting logic
```

Speaker amplifier may use battery/5 V directly if appropriate.

Calculate current requirements before selecting the regulator.

Provide reasonable headroom for:

- ESP32 Wi-Fi peaks
- display backlight
- audio amplifier
- haptic motor
- RGB LEDs

# Programming

Use ESP32 native USB programming if supported by the selected module.

Also provide accessible:

- BOOT
- RESET

Do not rely on tiny inaccessible pads for initial bring-up.

---

# PCB target

Target board size approximately:

**50 mm × 45 mm**

The exact dimensions can change slightly to support good ergonomics and RF/mechanical layout.

Aim for a rounded-rectangle handheld/keychain-style PCB.

Add:

- four mounting holes if useful for enclosure assembly
- mounting dimensions documented
- no components interfering with screw heads
- optional lanyard/keychain mounting hole

Prefer a **4-layer PCB**:

```text
L1 – Components + signals
L2 – Solid GND
L3 – Power + slower signals
L4 – Signals
```

Maintain a strong continuous ground plane.

---

# Placement priorities

Placement must be completed before routing.

Important placement rules:

1. ESP32 antenna at board edge.
2. Respect full antenna keepout.
3. USB-C at bottom edge.
4. Display centered in upper/front area.
5. TALK button easy to reach.
6. APPROVE and REJECT separated enough to avoid accidental presses.
7. Encoder accessible with thumb.
8. MEMS microphones near exposed enclosure openings.
9. Charger and regulator kept away from microphone analog/acoustic area.
10. Speaker amplifier kept away from sensitive microphone signals.
11. Battery connector positioned for sensible enclosure wiring.
12. Debug controls accessible.
13. All connectors accessible from enclosure edges where appropriate.

# JLCPCB requirement

The design is intended to be manufactured with **JLCPCB PCBA**.

For every important component, determine:

- manufacturer
- exact manufacturer part number
- LCSC/JLCPCB part number
- package
- basic/extended classification if known

Create a BOM table similar to:

| Ref | Function | Part | Manufacturer | MPN | LCSC/JLCPCB | Package | Qty |
|---|---|---|---|---|---|---|---|

Do not guess LCSC numbers.

Verify every supplier part before using it.

Avoid obscure components when an easier JLCPCB-supported alternative exists.

# Privacy requirement

This is important.

The microphone privacy switch must provide a **hardware-level microphone disable**.

When privacy is OFF:

```text
MIC POWER = physically disconnected
```

Firmware must not be able to secretly re-enable the microphones while the physical switch is in the disabled position.

A visible privacy indication should also be considered.

# Design philosophy

The final product should feel like:

> A small physical remote control for an AI agent.

Not:

> A smartphone replacement.

Keep it:

- compact
- understandable
- manufacturable
- repairable
- low power
- visually clean
- easy to assemble
- easy to debug

Prioritize reliability over unnecessary complexity.
